mTLS and PKI: how a Kubernetes cluster proves who is who

Keys, certificates, CAs and mTLS: learn the idea once, then watch it run through every connection in a cluster.

1PKI and mTLS basics

Five ideas, each one fixing the gap the previous one leaves open. That is all the theory the diagram needs.

  1. Key pair: a signature only the owner can make

    Two linked keys. The private key (*.key) is secret and signs. The public key is shared and checks the signature, so a valid signature proves “I hold the private key” without sending it. Gap: a key has no name. Anyone can claim a public key belongs to the API server.

  2. Certificate: a public key tied to a name

    A file (*.crt) holding a name (Subject), the public key, dates, a SAN (the DNS names and IPs a server may be reached at) and a CA’s signature over all of it. Public, safe to show. Gap: a self-signed one proves nothing. We need a signer everybody trusts.

  3. CA: the signer everybody trusts

    Just two files: ca.key (signs, secret) and ca.crt (public). Not a server; nothing runs it. Its own certificate is self-signed, which is where trust starts. Issuing: the owner makes its key pair → sends a CSR (public key + wanted name, nothing secret) → the CA signs it → the certificate comes back. The private key never travels.

  4. Trust: a file you hold

    You trust a CA by holding its ca.crt. No call to the CA is needed. A certificate passes four checks: a its signature verifies with ca.crt; b the address you dialled is in the SAN; c today is inside the dates; d the sender signs the handshake with the matching private key, so a copied certificate is useless.

  5. TLS and mTLS

    TLS: only the server shows a certificate (a website). mTLS: the client shows one too, and the server checks it with its own ca.crt. In Kubernetes, Pods and SSO logins show a token (a signed note, a JWT) instead of a client certificate.

Rule for every diagram

The answerer (server) always shows its certificate first. The dialer (client) checks it, then shows its own certificate (mTLS) or a token.

2The three CAs

Every certificate must be signed by someone, and whoever checks it must hold that signer’s public file. So kubeadm creates three CAs at install, one per kind of trust. Each is two files: ca.key signs (secret), ca.crt is what everyone else holds to verify. A certificate from one CA is rejected by the other two.

  • kubernetes-ca (/etc/kubernetes/pki/ca.crt + ca.key): the main signer. It signs the API server’s own certificate and every client identity: users, kubelets, scheduler, controller-manager. Holding its ca.crt is how a client trusts the API server, and how the API server checks clients.
  • etcd-ca (pki/etcd/ca.crt + ca.key): signs only etcd’s certificates and the API server’s client certificate for etcd. Kept separate because etcd holds every Secret, so a certificate from kubernetes-ca must not open it.
  • front-proxy-ca (pki/front-proxy-ca.crt + .key): signs exactly one certificate, front-proxy-client.crt, which the API server shows to extension APIs such as metrics-server. It means “trust the user name I forward”, so ordinary clients must never be able to get one.

The one bridge

Only the API server holds a certificate from all three CAs: apiserver.crt (kubernetes-ca), apiserver-etcd-client.crt (etcd-ca) and front-proxy-client.crt (front-proxy-ca). Every other component lives in one world. The table shows who holds which ca.crt.

Not CAs, but also trust anchors

sa.key / sa.pub sign and verify Pod tokens (a bare key pair, no certificate). The IdP’s public keys (JWKS) verify SSO tokens. Neither signs certificates.

Where, how long, if lost

Workers hold only ca.crt; HA control planes share the same three CAs; EKS/GKE/AKS keep them for you. kubeadm defaults: CAs 10 years, other certificates 1 year. Lose ca.key and nothing new can be signed or renewed.

The CAs: where every certificate comes from

Signing
The demo

The admin runs sudo kubeadm init --control-plane-endpoint k8s.example.com:6443 on a fresh server called cp-1. Nothing exists yet. Watch what appears on disk.

Before any connection can happen, someone has to create the CAs and sign every certificate. In a kubeadm cluster that someone is the kubeadm command. It is not a service: it runs, writes files, and exits.

Step by step · each numbered pointer on the diagram is one of these steps. Hover a step to light its pointer.

  1. kubeadm creates three CAs

    It generates three key pairs. In each pair the private key (ca.key) stays secret, and the matching public key is written into the certificate (ca.crt), which the CA signs with its own private key. "Self-signed" means Issuer and Subject are the same: nobody vouches for it, and everyone trusts it only because the file was placed there.

    /etc/kubernetes/pki/ca.crt              CN=kubernetes-ca
/etc/kubernetes/pki/front-proxy-ca.crt    CN=kubernetes-front-proxy-ca
/etc/kubernetes/pki/etcd/ca.crt          CN=etcd-ca
    ca.crtca.key

  2. It signs the API server's certificates

    For each job kubeadm makes a new key pair, puts the public key into a certificate, and signs that certificate with the matching CA's private key. The private half stays beside it as a .key file. The serving certificate gets a SAN for every name clients will use, including the load balancer, or kubectl would later refuse it.

    Which CA signs which? apiserver.crt comes from kubernetes-ca; apiserver-etcd-client.crt from etcd-ca (next step); front-proxy-client.crt from front-proxy-ca. Clients later verify apiserver.crt against their copy of kubernetes-ca’s ca.crt (chapter 3).

    apiserver.crt   Issuer: CN=kubernetes-ca
  SAN: DNS:k8s.example.com, DNS:kubernetes.default.svc, IP:10.96.0.1, IP:192.168.1.10
    apiserver.crtapiserver-etcd-client.crtfront-proxy-client.crt

  3. It signs the etcd certificates

    etcd-ca signs etcd's server certificate, its peer certificate, and the API server's etcd client certificate. kubernetes-ca plays no part here.

    etcd/server.crt  Issuer: CN=etcd-ca   SAN: 127.0.0.1, localhost, 192.168.1.10
    etcd/server.crtetcd/peer.crt

  4. It writes the kubeconfig files

    admin.conf, controller-manager.conf and scheduler.conf each embed a client certificate signed by kubernetes-ca, together with its private key. admin.conf carries O=kubeadm:cluster-admins (bound to cluster-admin); super-admin.conf (v1.29+) carries O=system:masters, which bypasses RBAC, so guard it. It exists only on the node where kubeadm init ran. A control-plane node added later with kubeadm join --control-plane gets its own admin.conf, controller-manager.conf, scheduler.conf and kubelet.conf, signed by the same CA, but no super-admin.conf. The first node’s own kubelet.conf is made the same way.

    scheduler.conf        client cert: CN=system:kube-scheduler
controller-manager.conf client cert: CN=system:kube-controller-manager
admin.conf            client cert: CN=kubernetes-admin, O=kubeadm:cluster-admins
    scheduler.conf

  5. It creates the token key pair

    sa.key (private) and sa.pub (public) are a bare key pair: not a CA, no certificate around the public key. Later the API server signs Pod tokens with the private one and verifies them with the public one (conversation 12).

    sa.keysa.pub

  6. It writes the static Pod manifests

    Each manifest in /etc/kubernetes/manifests carries flags that point at those files. The kubelet watches that folder and starts the control-plane Pods. That is why a path can always be found by reading a manifest (chapter 5).

    kube-apiserver.yaml:   --tls-cert-file=/etc/kubernetes/pki/apiserver.crt

  7. kubeadm exits; one CA key stays busy

    Leaf certificates last one year, the CAs ten. From now on only the controller-manager keeps loading ca.key, to sign certificate requests (conversations 2, 8 and 9). The etcd and front-proxy CA keys sit idle.

    ca.key

  8. Remote holders get theirs later

    The admin gives Seema a copy of admin.conf (or Seema asks for her own certificate through the CSR API). Each worker's kubelet gets its certificate when it joins (conversation 8).

    seema.crt

How Seema joins the cluster: key pair, CSR, ca.crt and RBAC

Certificate way (original)
The demo

Seema is a new developer. She has a laptop and nothing else: no certificate, no kubeconfig, and she has never seen the cluster CA. By the end she can run kubectl get pods -n dev. This is the original, still fully supported way to add a person. Conversations 3 and 5 are the modern way: set up once, then log in daily.

A cluster keeps no list of users. Seema becomes known in three separate steps: she makes her own key pair, the cluster CA signs a certificate that binds her public key to her name, and a RoleBinding gives that name some rights.

Step by step · each numbered pointer on the diagram is one of these steps. Hover a step to light its pointer.

  1. Seema makes her own key pair

    On her laptop she generates a key pair. The private key never leaves the laptop. The matching public key is derived from it mathematically, and it is the only half that will ever travel.

    $ openssl genrsa -out seema.key 2048
$ openssl pkey -in seema.key -pubout
-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A…
-----END PUBLIC KEY-----
    seema.key

  2. She makes a certificate request (CSR)

    The CSR holds three things: her public key, the name she asks for (CN=seema, O=dev-team), and a signature made with seema.key that proves she owns the private half. It contains no secret, so it is safe to send.

    $ openssl req -new -key seema.key -out seema.csr -subj "/CN=seema/O=dev-team"
    seema.csr

  3. She sends the CSR to an admin

    Seema has no credentials yet, and the Kubernetes API demands authentication, so someone who is already inside has to file the request for her. Chat, ticket or email is fine, because a CSR is public.

  4. The admin files a CertificateSigningRequest

    Authenticated with his own admin.conf (the same handshake as conversation 4), the admin creates the object. signerName says "sign this so the API server accepts it as a client certificate", and expirationSeconds asks for a short life, one day here (the minimum is 10 minutes, and the controller-manager’s --cluster-signing-duration caps it).

    kind: CertificateSigningRequest
spec:
  request: <base64 of seema.csr>
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 86400
  usages: [client auth]

  5. The admin approves it

    This signer is never approved automatically, so a human decides. He reads the requested name first: never approve O=system:masters, which would bypass RBAC for good.

    $ kubectl get csr
seema   kube-apiserver-client   Pending
$ kubectl certificate approve seema

  6. The controller-manager signs it

    Its signing controller uses kubernetes-ca’s private key (ca.key) to sign over Seema’s public key and name. The result is a certificate: her public key + her name + dates + the CA’s signature. It lands in the request’s status.

    Subject: CN=seema, O=dev-team
Issuer:  CN=kubernetes-ca
Not After: tomorrow   (one day)
    ca.key

  7. She receives seema.crt and ca.crt

    The admin exports the certificate and hands Seema two files: seema.crt, and the cluster’s ca.crt, the CA’s public certificate (the same file as /etc/kubernetes/pki/ca.crt). She checks the ca.crt fingerprint with the admin over a second channel, because this file decides who she will trust later.

    $ kubectl get csr seema -o jsonpath='{.status.certificate}' | base64 -d > seema.crt
$ openssl x509 -in ca.crt -noout -fingerprint -sha256
    seema.crtca.crt

  8. She builds her kubeconfig

    Now her kubeconfig holds everything the handshake in conversation 4 needs: the CA to trust the server, her certificate, and her private key.

    $ kubectl config set-cluster demo --server=https://k8s.example.com:6443 \
    --certificate-authority=ca.crt --embed-certs=true
$ kubectl config set-credentials seema --client-certificate=seema.crt \
    --client-key=seema.key --embed-certs=true
$ kubectl config set-context seema@demo --cluster=demo --user=seema
    ca.crtseema.crtseema.key

  9. Why the cluster trusts her, and what she may do

    The cluster never stored Seema anywhere. It trusts her certificate for one reason: kubernetes-ca signed it, and the API server trusts kubernetes-ca (--client-ca-file). Her permissions come from a RoleBinding that names her group. Without a binding she would be authenticated, but allowed to do nothing.

    $ kubectl create rolebinding dev-edit --clusterrole=edit --group=dev-team -n dev
$ kubectl --context seema@demo auth whoami
Username  seema     Groups  [dev-team system:authenticated]

A certificate cannot be revoked. It works until it expires, unless you remove every RoleBinding for her name. That is why the short expirationSeconds matters, and why SSO (conversations 3 and 5) is the better everyday login for people. Keep certificates for machines and break-glass admin access.

SSO setup, done once: IdP, API server, public keys, RBAC and laptop

One-time setup (authentication + authorization)
The demo

Weeks before Seema’s first day, the platform admin connects the cluster to the company SSO (keycloak.example.com). Steps 1 to 4 are the admin’s and are done once; step 5 is Seema’s own laptop, also once; step 6 proves it works. The cluster never registers “Seema”: she is only a user and a group at the IdP.

Two sides have to learn about each other, once. The IdP learns that an application called k8s-cluster may ask for tokens. The API server learns which issuer to trust, which audience to expect, how claims become user and group names, and then fetches the IdP’s public keys by itself. Since v1.34 this is Structured Authentication Configuration (stable; v1.29 alpha, v1.30 beta). Steps 1, 2, 3 and 5 are authentication (who is she?), step 4 is authorization (what may she do?), and step 6 tests both.

Step by step · each numbered pointer on the diagram is one of these steps. Hover a step to light its pointer.

  1. Configure the IdP: realm, group, user, client and groups claim (the Keycloak admin UI)

    The IdP admin teaches Keycloak that an app called k8s-cluster may ask for tokens, and what goes inside them. Menu names move a little between Keycloak versions; the settings are what matter. Any other IdP (Entra ID, Okta, Dex) needs the same four things: an issuer URL, a client ID, a username claim and a groups claim.

    1. Realm. Create company. The issuer URL is https://keycloak.example.com/realms/company (older Keycloak versions put /auth before /realms). It must be https, and the hostname the API server dials must be in Keycloak’s certificate.
    2. Group and user. Groups → create dev-team. Users → add seema, Credentials → set a password (switch “temporary” off), Groups → join dev-team.
    3. Client. Clients → Create client: type OpenID Connect, Client ID k8s-cluster. Client authentication OFF (a public client: no secret to leak), Standard flow ON, Direct access grants OFF. Valid redirect URIs http://localhost:8000/* and http://localhost:18000/* (kubelogin listens on 8000 and falls back to 18000). Advanced → PKCE method S256. The client ID becomes the token’s aud. A confidential client also works, but then every laptop’s kubeconfig must hold its secret.
    4. Groups claim. Client → Client scopes → k8s-cluster-dedicated → Add mapper → Group Membership: Name and Token Claim Name groups, Full group path OFF, Add to ID token ON. With the path ON the claim holds /dev-team and every binding would need keycloak:/dev-team.
    5. Check it from the control-plane node. The issuer printed must equal, character for character, the URL you give the API server in step 2.
    curl -s https://keycloak.example.com/realms/company/.well-known/openid-configuration \
  | jq '{issuer, jwks_uri}'
    signing key

  2. Tell the API server which issuer to trust (on every control-plane node)

    Pick one route. Route 1 is the structured file: stable since v1.34, several issuers, CEL rules, and later edits are picked up without a restart. Route 2 is the older --oidc-* flags, still supported. Mixing them makes the API server refuse to start.

    apiVersion: apiserver.config.k8s.io/v1
kind: AuthenticationConfiguration
jwt:
- issuer:
    url: https://keycloak.example.com/realms/company   # = "issuer" in discovery doc
    audiences: [k8s-cluster]                                # client ID (step 1)
    # certificateAuthority: |                               # private CA only (PEM)
  claimMappings:
    username: {claim: preferred_username, prefix: "keycloak:"}
    groups:   {claim: groups,            prefix: "keycloak:"}
    • url is the issuer (flag --oidc-issuer-url), audiences the client ID. If you also set discoveryURL, the issuer inside that document must still equal url.
    • Nothing is defaulted. You must set the username claim and its prefix (even an empty one), and a groups prefix whenever you map groups. The prefix keeps IdP names apart from system: names and from other IdPs.
    • Optional claimValidationRules and userValidationRules (CEL) can reject tokens, for example unverified emails.

    Now make the API server read it: mount the file’s directory and add the flag. Editing the static pod manifest is enough, because the kubelet recreates the pod when the file changes (keep backup copies outside that directory, or the kubelet starts them as extra pods).

    # /etc/kubernetes/manifests/kube-apiserver.yaml
spec:
  containers:
  - command:
    - kube-apiserver
    - --authentication-config=/etc/kubernetes/auth/authentication-config.yaml   # add
    # ...existing flags stay...
    volumeMounts:
    - {name: auth-config, mountPath: /etc/kubernetes/auth, readOnly: true}     # add
  volumes:
  - name: auth-config                                                          # add
    hostPath: {path: /etc/kubernetes/auth, type: Directory}
    +Making it survive kubeadm upgrades

    kubeadm rewrites the manifests on upgrade, so a hand edit can disappear. Keep the same flag and volume in ClusterConfiguration instead (see “Reconfiguring a kubeadm cluster” in the kubeadm docs).

    apiVersion: kubeadm.k8s.io/v1beta4

  extraArgs:
  - name: authentication-config
    value: /etc/kubernetes/auth/authentication-config.yaml
  extraVolumes:
  - name: auth-config
    hostPath: /etc/kubernetes/auth

    readOnly: true
    pathType: Directory
    +Route 2: the legacy flags instead of the file

    Add these under spec.containers.command and leave out --authentication-config. The kubeadm API server pod already mounts /etc/kubernetes/pki, so a CA file placed there is visible; any other directory needs its own volume.

        - --oidc-issuer-url=https://keycloak.example.com/realms/company   # note the /realms/<realm> path
    - --oidc-client-id=k8s-cluster                                         # the client ID from step 1

    - --oidc-username-prefix=keycloak:                                     # avoids clashes with other users
    - --oidc-groups-claim=groups                                           # must match the mapper's claim name
    - --oidc-groups-prefix=keycloak:
    # private CA only: - --oidc-ca-file=/etc/kubernetes/pki/keycloak-ca.crt

    Then check that it came back. kubectl may fail for a minute while the pod restarts.

  | grep -E 'authentication-config|oidc'
sudo crictl ps -a | grep kube-apiserver     # stuck? crictl logs <container-id>

  3. The API server discovers the IdP and downloads its public keys (JWKS)

    Nobody pastes these keys into the cluster. When the API server loads the file it reads {issuer.url}/.well-known/openid-configuration (or discoveryURL), checks that the issuer inside equals the configured URL, takes jwks_uri from it, and downloads the JWKS over HTTPS. The keys are public, so nothing needs protecting: they are held in the API server’s memory. They are not in /etc/kubernetes/pki, not in etcd, not in a ConfigMap. The IdP does not even have to be reachable when the API server starts.

    Rotation. When the IdP rotates its signing key, new tokens name a new kid. The API server re-downloads the JWKS when it meets a key id it does not hold, so the admin does nothing. (This is how the upstream OIDC library behaves; the Kubernetes docs do not spell out the refresh rules.)

    GET https://keycloak.example.com/realms/company/.well-known/openid-configuration
  issuer:   https://keycloak.example.com/realms/company      (must equal issuer.url)
  jwks_uri: https://keycloak.example.com/realms/company/protocol/openid-connect/certs

    IdP public keys (JWKS)

  5. Configure the developer’s laptop: kubelogin and the kubeconfig (once per person)

The demo

Step by step · each numbered pointer on the diagram is one of these steps. Hover a step to light its pointer.

  1. kubectl reads ~/.kube/config

    It finds where to connect, a copy of the cluster CA certificate (which holds the CA's public key), Seema's certificate (which holds her public key) and her private key.

    server: https://k8s.example.com:6443

  2. The laptop connects and sends ClientHello

    It opens TCP to 203.0.113.10:6443, which is the load balancer. The load balancer forwards the raw bytes to cp-1 without opening them, so the TLS handshake is still between kubectl and the API server.

  3. The API server shows apiserver.crt

    It sends apiserver.crt, which carries the API server's public key, and signs the handshake with apiserver.key (the private half). Anyone can copy a certificate; only the owner of the private key can make that signature.

    Subject: CN=kube-apiserver
Issuer:  CN=kubernetes-ca
SAN:     DNS:k8s.example.com, DNS:kubernetes.default.svc, IP:10.96.0.1, IP:192.168.1.10
Not After: Oct 14 2027
    apiserver.crt

  4. kubectl checks it

    Four checks, a to d, as in chapter 1. a The certificate’s signature verifies with the CA public key in ca.crt, so the certificate is genuine. b k8s.example.com is in the SAN. c The dates are valid. d The server’s public key, taken from the certificate, verifies the handshake signature, which proves the sender holds apiserver.key. If the SAN lacked the load-balancer name, Seema would see x509: certificate is valid for …, not k8s.example.com.

    ca.crt

  5. The API server asks for her certificate

    It was started with --client-ca-file, so it requests a client certificate. It only asks: the server does not reject a client that has none (the source sets RequestClientCert), which is why SSO and Pod logins can connect without one. kubectl sends seema.crt, which carries Seema's public key, and signs the handshake with seema.key. Anyone can copy a certificate; only the owner of the private key can produce a signature that Seema's public key accepts.

    Subject: CN=seema, O=dev-team
Issuer:  CN=kubernetes-ca
    seema.crtseema.key

  6. The API server verifies and reads her identity

    The same checks again, minus the SAN check (a client has no server name): The certificate's signature is verified with the CA public key in its --client-ca-file, and the handshake signature is verified with Seema's public key from the certificate. Both pass, so this really is seema. CN=seema becomes the user name and O=dev-team a group. No user database was consulted: how Seema got this certificate is the story of conversation 2.

    user=seema   groups=[dev-team, system:authenticated]
    ca.crt

  7. The handshake finishes and both sides switch to session keys

    In TLS 1.3 the ephemeral key exchange already happened in the two Hellos, so every certificate above travelled encrypted (TLS 1.2 sent them in the clear). The Finished messages confirm nothing was tampered with, then both sides switch to the application keys: from here on everything, including the URL path, is encrypted.

  8. RBAC decides, and etcd answers

    A RoleBinding in dev says dev-team may list Pods, so the request goes ahead. Without it Seema would get 403 Forbidden, not 401: the server knows exactly who she is, it just says no. For the data, the API server asks etcd (conversation 7) and the table comes back through the same tunnel.

    GET /api/v1/namespaces/dev/pods   →  200 OK

Seema → API server (SSO): certificates first, then the token, every day

Daily use (TLS + ID token)
The demo

Monday morning. The setup in conversation 3 was done weeks ago. Seema’s cached token expired overnight and she runs kubectl get pods -n dev. Her kubeconfig has no certificate and no private key at all.

Nothing is registered again, and every hop follows one rule: the answerer shows its certificate first, the dialer shows its credential second. First the IdP shows its certificate and Seema logs in. Then the API server shows apiserver.crt, kubectl shows the ID token, and the API server verifies it with the IdP public keys it has held since conversation 3.

Step by step · each numbered pointer on the diagram is one of these steps. Hover a step to light its pointer.

  1. kubectl starts the credential plugin

    Her kubeconfig has no certificate and no private key. Instead it tells kubectl to run a helper program whenever it needs credentials, called an exec credential plugin. kubelogin is the common one.

    users:
- name: seema
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1
      command: kubectl
      args: [oidc-login, get-token, --oidc-issuer-url=https://keycloak.example.com/realms/company, --oidc-client-id=k8s-cluster]

  2. The IdP (answerer) shows its certificate first; the browser checks it

    Before any password is typed, the login page is an ordinary TLS connection, and the answerer speaks first: the IdP sends its certificate, signed by a public CA. The browser checks the signature, that the name is keycloak.example.com, and the dates, using the operating system’s trust store. Only then does Seema type anything. The cluster CA plays no part here.

    Subject: CN=keycloak.example.com   Issuer: a public CA
trusted through the OS trust store, not through ca.crt

  3. She logs in at the IdP

    kubelogin opens her browser; once the page is trusted (step 2) she types her password and approves MFA. Her password goes to the IdP only, never to kubectl or Kubernetes. This is the OIDC authorization-code flow, with PKCE (kubelogin supports it through --oidc-pkce-method) so a stolen code is useless.

  4. The IdP issues signed tokens

    The IdP signs an ID token (a JWT) with its private signing key and returns it with a refresh token. kubelogin collects them over TLS from the IdP’s token endpoint (checking the IdP certificate again) and caches both under ~/.kube/cache/oidc-login. Anyone can read the payload; nobody can change it without breaking the signature.

    iss:    https://keycloak.example.com/realms/company
aud:    k8s-cluster
preferred_username: seema
groups: [dev-team]
exp:    (about an hour from now)
    ID tokenrefresh token

  5. The API server (answerer) shows apiserver.crt first; kubectl checks it

    Second connection: kubectl dials :6443. The answerer goes first again: the API server sends apiserver.crt and signs the handshake with apiserver.key. kubectl runs four checks with the ca.crt from her kubeconfig: a the signature verifies, b the name she dialled (the load balancer too) is in the SAN, c the dates are valid, d the handshake signature verifies with the cert’s public key. The API server asks for a client certificate but does not insist on one; she has none. SSO replaces her client certificate, never the server’s.

    apiserver.crt   Issuer: CN=kubernetes-ca
kubectl: signature OK · SAN OK · dates OK · handshake OK  → channel trusted
    ca.crt

  6. kubectl (dialer) shows its credential: the ID token

    Only now, inside the trusted channel, kubectl shows who she is: the cached ID token in the Authorization header. No client certificate is sent. The token is safe to send because it goes only to a server that just proved itself in step 5.

    GET /api/v1/namespaces/dev/pods
Authorization: Bearer eyJhbGciOiJSUzI1NiIs…

  7. The API server verifies the token, field by field

    a kid in the token header picks a public key from the JWKS it already holds, and the signature must verify with it: the IdP issued it and nobody edited it. b iss equals the configured issuer.url. c aud contains at least one configured audience (k8s-cluster). d exp is in the future. The claim you mapped to the username must be present too. e Any claimValidationRules you wrote (CEL) pass. f The claim mapping builds her identity: username and groups, each with its prefix. Normally this uses keys held since conversation 3, so no call to the IdP happens.

    user=keycloak:seema  groups=[keycloak:dev-team, system:authenticated]

  8. RBAC decides, and the session stays fresh

    The binding from conversation 3 allows the read. About an hour later the ID token expires and kubelogin quietly gets a new one with the refresh token. When Seema leaves the company, the admin disables her at the IdP: her refresh stops working and Kubernetes needs no change at all.

What happens on each kubectl call: a valid cached ID token is reused; an expired one is renewed silently with the refresh token; only when the refresh token is gone or revoked does the browser open again.

Managed clouds use the same exec-plugin mechanism with their own IAM as the identity provider: aws eks get-token, gke-gcloud-auth-plugin, Azure kubelogin. For CI and other automation, use a ServiceAccount token instead of a person’s login.

A new node joins: kubelet CSR bootstrapping

Token, then mTLS
The demo

The team adds a server called worker-2 (192.168.1.22). It is a blank machine with a kubelet installed, and it has no certificate and no reason to trust anyone.

kubeadm join solves this chicken-and-egg problem with a short-lived token plus a hash of the cluster CA’s public key. The node ends up with its own private key and a certificate signed by kubernetes-ca, and the token is thrown away.

Step by step · each numbered pointer on the diagram is one of these steps. Hover a step to light its pointer.

  1. The control plane prepares a token and cluster-info

    On cp-1 the admin runs kubeadm token create. The public ConfigMap cluster-info in kube-public already holds the cluster CA certificate and a signature made with the token.

    $ kubeadm token create --print-join-command
kubeadm join k8s.example.com:6443 --token abcdef.0123456789abcdef \
  --discovery-token-ca-cert-hash sha256:9f2c…e41b

  2. The admin runs kubeadm join on worker-2

    The --token proves worker-2 was invited. The --discovery-token-ca-cert-hash is a SHA-256 hash of the cluster CA’s public key, copied from a place the admin trusts.

  3. Discovery: "is this really my cluster?"

    worker-2 downloads cluster-info, checks its signature with the token, and checks that the public key of the CA inside hashes to the pinned value. Only then does it save ca.crt and trust the API server. The very first download of cluster-info ignores TLS errors, because nothing is trusted yet: the token signature and the CA hash do that job instead.

    /etc/kubernetes/pki/ca.crt   (new on worker-2, public CA only)
    ca.crt

  4. The kubelet creates its own key and a request

    A new key pair is generated on worker-2. The private key never leaves it. The CSR carries only the public key and the name system:node:worker-2 (group O=system:nodes), plus a signature proving worker-2 owns the private half.

    CSR  CN=system:node:worker-2, O=system:nodes
     signerName: kubernetes.io/kube-apiserver-client-kubelet
    kubelet key

  5. The API server shows its certificate first; then the kubelet shows its token

    worker-2 now dials the API server and trusts it with the ca.crt saved in step 3. The answerer goes first: the API server shows apiserver.crt and the kubelet runs the four checks. Only then does it show the bootstrap token (a Bearer token) and submit the CSR. The token maps to the user system:bootstrap:abcdef in group system:bootstrappers:kubeadm:default-node-token, and RBAC lets that group create node CSRs.

  6. The controller-manager approves and signs

    It sees the CSR through its normal connection (conversation 6), auto-approves it (the csrapproving controller) and signs it (the csrsigning controller) with ca.crt and ca.key. This is how a CA key is used while the cluster runs: the controller-manager signs every certificate request, including Seema’s (conversation 2) and the renewals in conversation 9.

    $ kubectl get csr
csr-x7k2p   system:bootstrap:abcdef   kube-apiserver-client-kubelet   Approved,Issued
    ca.key

  7. The signed certificate comes back

    worker-2's kubelet picks it up from the CSR's status.

  8. From now on it is a normal node

    The kubelet saves the certificate, writes kubelet.conf, stops using the bootstrap token, and authenticates with the certificate from now on (conversation 9). The token expires on its own after 24 hours, and worker-2 never held ca.key.

The demo

Seema wants to read a log: kubectl logs payments-7d9f4 -n shop. The Pod runs on worker-1, so the API server has to fetch the log from that node's kubelet.

This one runs the other way round. For logs and exec the API server becomes the client and the kubelet the server. That role swap compared with conversation 9 is why it is called "reverse mTLS".

Step by step · each numbered pointer on the diagram is one of these steps. Hover a step to light its pointer.

  1. Seema's request arrives and RBAC allows it

    The highlighted path from her laptop is conversation 4: she is authenticated, and a Role lets her use pods/log in shop.

    kubectl logs payments-7d9f4 -n shop

  2. The API server finds the node and dials it

    The Pod's node is worker-1; its address is in the Node object. The API server connects to 192.168.1.21:10250.

    By default this certificate is self-signed, and the API server does not verify it, because kubeadm leaves --kubelet-certificate-authority unset. Verifying it is a hardening step: let each kubelet request a certificate from kubernetes-ca (serverTLSBootstrap: true; these kubelet-serving requests are never auto-approved, so an admin approves them) and set --kubelet-certificate-authority.

    Subject: CN=worker-1   Issuer: CN=worker-1-ca@1697…   (self-signed)
    kubelet serving cert

    The API server answers with its dedicated kubelet-client certificate. Its group kubeadm:cluster-admins is bound to cluster-admin. It only asks: a caller with no valid credential would be anonymous, and kubeadm turns anonymous access off.

    Subject: CN=kube-apiserver-kubelet-client, O=kubeadm:cluster-admins

    ca.crt

    The kubelet reads the container's log from the runtime and sends it to the API server, which passes it to kubectl. Each hop is encrypted separately, and the Pod itself is not a party to any of it.

Pod ⟷ kube-apiserver (ServiceAccount token)

TLS + token (not mTLS)
The demo

The Pod payments-7d9f4 in namespace shop runs on worker-1 and needs to read a ConfigMap through the API. It has no certificate. How does the API server know who it is?

By default a Pod has no certificate. It carries a short-lived signed token that the API server issued for it, and it checks the server with a copy of the CA. One side shows a certificate, the other a token: TLS plus a bearer token, not mTLS.

Step by step · each numbered pointer on the diagram is one of these steps. Hover a step to light its pointer.

  1. The Pod is scheduled to worker-1

    The kubelet there sees which ServiceAccount the Pod uses: payments-sa.

  2. The kubelet asks the API server for a token

    A TokenRequest over its own mTLS connection (conversation 9), naming the Pod. NodeRestriction lets a kubelet ask only for Pods on its own node.

  3. The API server signs a JWT

    Signed with the private key sa.key, bound to this Pod and ServiceAccount, with an audience and a short expiry. It goes back to the kubelet.

    sub: system:serviceaccount:shop:payments-sa
aud: https://kubernetes.default.svc.cluster.local
exp: (about an hour from now)
    sa.key

  4. The kubelet writes the files into the Pod

    Into an in-memory volume at /var/run/secrets/kubernetes.io/serviceaccount/: the token, a ca.crt copied from the ConfigMap kube-root-ca.crt, and the namespace.

    /var/run/secrets/kubernetes.io/serviceaccount/token
/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
/var/run/secrets/kubernetes.io/serviceaccount/namespace
    tokenca.crt

  5. The API server shows apiserver.crt first; the app checks it

    It calls https://kubernetes.default.svc. The Service IP 10.96.0.1 forwards to the API server on :6443. The Pod checks apiserver.crt with its ca.crt; that name and IP are in the certificate's SAN.

    ca.crt

  6. It sends the token

    In the header Authorization: Bearer <token>. No client certificate, and no Pod private key exists anywhere.

    GET /api/v1/namespaces/shop/configmaps
Authorization: Bearer eyJhbGciOiJSUzI1NiIs…

  7. The API server verifies the token

    Signature checked with the public key sa.pub (only the API server's own sa.key could have made it), then issuer, audience, expiry, and that the Pod and ServiceAccount still exist. The identity becomes system:serviceaccount:shop:payments-sa, and then RBAC decides.

    sa.pub

  8. The kubelet refreshes it

    Before the token expires, the kubelet repeats steps 2 to 4 and swaps the file in place. Your code must re-read the file instead of caching the token.

New in v1.37: a Pod can opt in to a real X.509 certificate through a podCertificate projected volume (kubelet-generated key, short-lived, auto-renewed). Tokens stay the default. And if a Pod never calls the API, set automountServiceAccountToken: false.

5Find any certificate yourself

Do not memorise paths. They differ between installers and versions. What never changes is the trail of breadcrumbs, and you can learn to follow it in three moves.

1

Find who uses it

Which Pod, systemd service or application needs this certificate?

2

Read how it was told

No program guesses where its certificate is. A flag, a kubeconfig or a volume names the file, and that instruction is written down.

3

Open the path and confirm

Run openssl x509 -noout -subject -issuer -dates on it. The subject and issuer tell you if it is the right one.

Try the method on each part of the cluster. Every tab uses the same three moves.

The API server's certificates

Which files does kube-apiserver use, and where are they?

1Find who uses it
kubectl -n kube-system get pods -l component=kube-apiserver
# kube-apiserver-cp-1   1/1   Running   ...
2Read how it was told where its certificates are

Every program has to be told where its files are. For a static Pod that instruction is in its command-line flags. Ask the Pod itself, from anywhere with kubectl:

kubectl -n kube-system get pod kube-apiserver-cp-1 -o yaml \
  | grep -E -- '--(client-ca|tls-|etcd-|kubelet-client|proxy-client|service-account)'
- --client-ca-file=/etc/kubernetes/pki/ca.crt
- --tls-cert-file=/etc/kubernetes/pki/apiserver.crt
- --tls-private-key-file=/etc/kubernetes/pki/apiserver.key
- --etcd-cafile=/etc/kubernetes/pki/etcd/ca.crt
- --etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt
- --kubelet-client-certificate=/etc/kubernetes/pki/apiserver-kubelet-client.crt
- --proxy-client-cert-file=/etc/kubernetes/pki/front-proxy-client.crt
- --service-account-key-file=/etc/kubernetes/pki/sa.pub

Or, on the control-plane node, read the manifest. Even the manifest folder is not a secret: the kubelet's config names it.

sudo grep staticPodPath /var/lib/kubelet/config.yaml
staticPodPath: /etc/kubernetes/manifests
sudo grep -- '-file' /etc/kubernetes/manifests/kube-apiserver.yaml
3Understand why the path works, then open it
kubectl -n kube-system describe pod kube-apiserver-cp-1 | grep -A8 -E 'Mounts:|Volumes:'
Mounts:
  /etc/kubernetes/pki from k8s-certs (ro)
Volumes:
  k8s-certs:
    Type:  HostPath (bare host directory volume)
    Path:  /etc/kubernetes/pki

sudo openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -subject -issuer -dates -ext subjectAltName

HostPath means the folder inside the container is that folder on the node. So the path in the flag is the real path on disk. And a Pod can only read what is mounted into it: the Volumes: section is a complete list of where its certificates can come from.

Which public key is inside a certificate?

A certificate always carries a public key. You can pull it out, and you can test whether a certificate and a private key belong together.

1Pull the public key out of a certificate
openssl x509 -in seema.crt -noout -pubkey
-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA…
-----END PUBLIC KEY-----
2Derive the public key from a private key
openssl pkey -in seema.key -pubout
# the private key file contains everything needed to compute its public half
3Do they match? The classic test
openssl x509 -in seema.crt -noout -pubkey | openssl sha256
openssl pkey -in seema.key -pubout            | openssl sha256
# identical hashes: this key belongs to this certificate

A certificate and key that do not match are a classic renewal mistake. A server that loads them stops with tls: private key does not match public key. The same trick works on any pair: apiserver.crt with apiserver.key, a kubelet .pem, and so on. A CSR holds the public key too: openssl req -in seema.csr -noout -pubkey.

8Doubts cleared

Q1Where is the public key? Is it a separate file?

Usually not. A public key almost always travels inside a certificate: seema.crt carries Seema's, apiserver.crt the API server's, ca.crt the CA's. Bare public-key files are rare. The main ones are sa.pub (verifies Pod tokens) and the identity provider's published JWKS (verifies SSO tokens). You can always extract one: openssl x509 -in seema.crt -noout -pubkey.

Q2How does the cluster know Seema? Where is she stored?

Nowhere. Kubernetes has no User object. With a certificate login it trusts her because kubernetes-ca signed a certificate with her name in it and the API server trusts kubernetes-ca (conversations 2 and 4). With SSO it trusts the identity provider's signature on her token (conversation 5). What she may do comes from RBAC bindings that name her or her group.

Q3How did Seema get ca.crt, and why should she be careful with it?

The admin gives it to her. It is the public file /etc/kubernetes/pki/ca.crt (it is also embedded in admin.conf and published in the cluster-info ConfigMap). She should confirm its SHA-256 fingerprint through a second channel, because whichever CA she trusts decides which API server she will believe. It is public, so there is no secret to leak, but a wrong one means being fooled.

Q4Why does Seema still need ca.crt if she logs in with SSO?

Two different questions. The SSO token tells the API server who she is. ca.crt lets her check that the server she is sending that token to is really the API server. Without it, an impostor could collect her token.

Q5Certificate login or SSO: which should people use?

SSO for day-to-day human access: short-lived tokens, MFA, groups, and one place to disable a leaver. Certificates still fit machines and a break-glass admin kubeconfig. Chapter 5 compares every option.

Q6Is a CA a server I have to run and keep alive?

No. A CA is two files. The signing is done by a command (kubeadm) or a controller (the controller-manager) that reads ca.key when needed. Stop every control-plane process and the CAs are still intact on disk.

Q7Do the three CAs have flows of their own?

No. A CA has no process and no traffic. What each CA has is a trust world: the certificates it signed and the components that accept them. In the diagram those are the three colours. Conversations 7 and 11 stay entirely inside the etcd and front-proxy worlds.

Q8Is Pod to API server really not mTLS?

Correct. The Pod verifies the server's certificate and the server verifies the Pod's token. The Pod has no client certificate by default. Pod Certificates, stable since v1.37, are the opt-in alternative: you choose a signer, run its signer controller, and the kubelet delivers and rotates a key and certificate through a podCertificate projected volume.

Q9Does a Pod authenticate to the kubelet?

Application Pods never talk to the kubelet; the kubelet talks to them (probes) with no authentication. Monitoring agents that call :10250 show their ServiceAccount token, and the kubelet checks it with the API server (conversation 13).

Q10Why does kubectl need ca.crt if it already has my client certificate?

They answer opposite questions. Your client certificate says who you are. ca.crt lets you check that the server really is your API server. Without it, someone on the network could pose as the server.

Q11What is sa.key? A fourth CA?

No. It is a bare key pair with no certificate, no name and no expiry. The API server signs Pod tokens with sa.key and verifies them with sa.pub. Nobody else needs to trust it.

Q12Does the load balancer need a certificate?

Not if it just forwards TCP to :6443 (the recommended setup). Its name must be in the API server certificate's SAN. If it ends TLS itself, client-certificate login breaks, because the API server never sees the client's certificate.

Q13What if I lose ca.key?

Everything issued keeps working until it expires, but you cannot sign anything new (joins, renewals). You would have to create a new CA and re-issue everything, which is a CA rotation.

Q14Does Seema (or the cluster) register with the IdP on every login?

No. The registration is done once by the admin (conversation 3): a client at the IdP and an AuthenticationConfiguration on the API server. After that Seema only logs in (conversation 5), which means she gets a fresh token. Nothing about the cluster is re-registered.

Q15Where do the IdP public keys live inside kube-apiserver? Is there a file?

No file. The API server reads the discovery document, follows jwks_uri, and downloads the JWKS over HTTPS into memory. It is not in /etc/kubernetes/pki, etcd or a ConfigMap, and a restart simply fetches it again. The IdP’s private key never leaves the IdP.

Q16What if the IdP rotates its keys, or is down?

A rotated key shows up as a new kid in new tokens, and the API server re-downloads the JWKS when it sees a key id it does not hold (upstream library behaviour; the docs do not detail the refresh rules). If the IdP is down, tokens that verify with keys already in memory keep working, but nobody can log in or refresh, so keep a break-glass certificate kubeconfig.

Q17Who signed apiserver.crt, and how does anyone know it belongs to this cluster?

kubernetes-ca signed it during kubeadm init. Clients know it is the cluster’s API server only because its signature verifies against the ca.crt they were given. There is no membership list; see the chapter 3 table of who holds which ca.crt.

If your cluster uses a different installer or an external CA, folders and lifetimes may differ. The trust relationships are the same.
