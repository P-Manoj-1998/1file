Part 1

Understand the solution

Read this part once. It explains every moving piece, so each later step makes sense.

1.1What you are building

Confirmed Working Architecture

  • The Kerberos keytab is stored in Azure Key Vault as a base64-encoded secret
  • Databricks reads that secret through a Key Vault-backed secret scope
  • Non-secret files krb5.conf, jaas.conf, and setup_kerberos.sh are stored in a Unity Catalog Volume
  • The cluster init script runs on every node at startup and:
  • decodes the keytab into /tmp/kerberos/app.keytab
  • copies krb5.conf into /tmp/kerberos/krb5.conf
  • copies jaas.conf into /tmp/kerberos/jaas.conf
  • The cluster Spark Config sets Java system properties pointing to those files
  • Kerberos authentication succeeds on the driver JVM
  • Data is distributed into Spark using spark.createDataFrame(...)
Two ingestion patterns are supported on top of this platform. Pattern A reads on the driver and suits small data. Pattern B logs in with a fresh identity inside every Spark task and suits large tables. See Parts 4 to 6.

1.2Glossary

Every term used in this guide, in the order you will meet them.

Term Definition
KDC Key Distribution Center — the Kerberos server that issues tickets. In Active Directory, this is a Domain Controller. Listens on TCP/UDP port 88.
TGT Ticket Granting Ticket — the initial ticket obtained from the KDC after authenticating with a keytab. Used to request service tickets without re-authenticating. Valid for ticket_lifetime (typically 10–24h).
Service Ticket A ticket scoped to one specific service (e.g., SQL Server). Obtained by presenting the TGT to the KDC along with the target SPN. SQL Server validates this ticket to confirm the client's identity.
SPN Service Principal Name — a unique identifier for a service instance registered in Active Directory. SQL Server format: MSSQLSvc/<FQDN>:<port>@<REALM>. Must be registered exactly once — duplicate SPNs break authentication. Verify with setspn -L <account>.
Keytab A binary file containing the long-term Kerberos encryption keys for a principal. Allows non-interactive (password-free) authentication. Treat exactly like a stored password. Never commit to source control, never store in DBFS or a volume without Key Vault protection.
KVNO Key Version Number — an integer that increments in Active Directory every time the account password changes. The KVNO in the keytab must match the current KVNO in AD. Mismatch causes Decrypt integrity check failed.
Enctype Encryption algorithm used for Kerberos keys. 18 = AES256-CTS-HMAC-SHA1-96 (required). 17 = AES128-CTS-HMAC-SHA1-96 (acceptable). 23 = RC4-HMAC (deprecated — reject this).
Realm The Kerberos administrative domain. Always uppercase by convention (e.g., PARENT.EXAMPLE.ORG). Each realm has its own KDC. Maps to an Active Directory domain.
Principal A Kerberos identity in the form name@REALM. For a service account: SVC-myaccount@DOMAIN.ORG. Must match exactly between keytab, jaas.conf, and Active Directory.
JAAS Java Authentication and Authorization Service — Java's pluggable authentication framework. The JDBC driver uses JAAS to locate the login module and keytab at connection time.
krb5.conf The Kerberos client configuration file. Tells the OS/JVM which realm is the default, where KDC servers are, and how hostnames map to realms. Must be present on every cluster node before the JVM starts.
jaas.conf The JAAS configuration file. Tells the JDBC driver's login module which keytab to use and which principal to load. The JAAS entry name MUST be exactly SQLJDBCDriver — the mssql-jdbc driver looks up this name by string.
Init Script A shell script that runs on every cluster node at startup, before Spark initialises. The only reliable way to stage Kerberos files on all nodes, including nodes added by autoscaling.
UC Volume Unity Catalog Volume — a UC-governed POSIX-style file store at /Volumes/<catalog>/<schema>/<volume>/. Used here to stage non-secret config files and the init script.
SINGLE_USER Databricks compute access mode where one identity (user or service principal) exclusively owns the cluster. Required because Standard (shared) mode does not support spark.executor.extraJavaOptions and restricts init scripts to an admin-managed allowlist.
UCS Unified Client Security — Databricks' internal security subsystem on SINGLE_USER and serverless clusters. Installs a custom AccessControlContext/DomainCombiner that intercepts privilege escalation. This is the confirmed root cause of executor-side Kerberos failure in this pattern.
DomainCombiner A Java security class that manages the combination of ProtectionDomain objects in security checks. The UCS DomainCombiner strips the Kerberos Subject from the security context during nested Subject.doAs → AccessController.doPrivileged calls on executor nodes.
Py4J The Python-to-Java bridge used by PySpark to call Java code from Python. Cannot pass raw Java Class<T> references as typed method parameters — a limitation that affects JVM credential inspection from Python.
GSS-API Generic Security Services API — the C/Java security abstraction layer that Kerberos sits on. Most Kerberos errors surface as GSSException: No valid credentials provided or GSS initiate failed.
Cross-Realm Auth When the Kerberos principal lives in one realm (e.g., PARENT.EXAMPLE.ORG) but the target service host is in a different DNS domain (e.g., child.example.org). Requires explicit [domain_realm] mapping in krb5.conf and a trust relationship between the realms in AD.

Cluster environment variables (secrets) Readable by any user who attaches to the cluster Only the assigned principal ever uses this cluster
Identity for Volume/init-script access Cluster owner The assigned principal (user or service principal)
Multiple users Many interactive users share one cluster One user or one service principal only
Use in this guide Never for Kerberos The only supported mode for the Kerberos JDBC cluster

Why Each Restriction Matters

spark.executor.extraJavaOptions not supported on Standard mode This is the critical blocker. Without spark.executor.extraJavaOptions, you cannot set -Djava.security.krb5.conf and -Djava.security.auth.login.config on executor JVMs. Without those, executors use the system-default Kerberos config (none on Databricks), and Kerberos auth fails on every executor.

Init script allowlist on Standard mode On Standard mode, init scripts must be explicitly allowlisted by a Databricks workspace admin. The allowlist is empty by default. This means any init script added to a Standard cluster without admin approval will be silently ignored — Kerberos files never staged, no error, silent failure at connection time.

Environment variable security The KERB_KEYTAB_B64 environment variable holds the base64-decoded keytab value (resolved from the Key Vault secret by Databricks at cluster start). On Standard mode, any other user who attaches to the cluster can read cluster environment variables and thereby exfiltrate the keytab. SINGLE_USER mode prevents this.

ADF Implication

When ADF triggers the Databricks job, the job cluster must be configured as SINGLE_USER assigned to the ADF service principal. ADF's service principal identity is what Databricks uses to read the UC Volume and resolve the secret scope during init script execution.

1.6Storage and secrets: what goes where and why

The Rule

If leaking the file lets someone impersonate the AD service account → it's a secret → Azure Key Vault. If it only reveals a realm name or hostname → it's configuration → UC Volume.

Storage Decision Table

File What It Contains Sensitivity Where It Lives Who Manages It
app.keytab Long-term Kerberos encryption keys for the service account SECRET — credential-equivalent Azure Key Vault, stored as base64 string, read via Key Vault-backed secret scope AD/Security team issues; Cloud/DevOps Databricks admin stores
krb5.conf Kerberos realm names and KDC hostnames Non-secret — hostnames only UC Volume (ADLS-backed) Cloud/DevOps Databricks admin; values sourced from AD team
jaas.conf Principal name and local keytab path Non-secret — no credentials UC Volume Cloud/DevOps Databricks admin
setup_kerberos.sh Init script logic Non-secret — no credentials UC Volume Cloud/DevOps Databricks admin

Key Vault Access Model

Permission model: Azure RBAC (not Vault access policy). Access is granted on the vault's IAM blade, not the legacy access-policy list.

What role is needed: Key Vault Secrets User (or equivalent custom role with the Microsoft.KeyVault/vaults/secrets/getSecret/action data action). The built-in Reader role only grants visibility into vault resource metadata — it does NOT allow reading secret values.

Who reads the secret: Databricks reads the secret through its own platform-level Azure AD application (the Databricks connector). This identity is granted the Key Vault Secrets User role on the vault. The cluster environment variable {{secrets/scope/key}} is resolved by Databricks at cluster start — the secret value is injected as a plain string into the init script environment.

Audit trail: Every single read of the keytab secret appears in the Key Vault audit log. This is one reason the keytab lives in Key Vault rather than a Volume with ACLs.

IMPORTANT DOCUMENTATION DISCREPANCY: Microsoft's own Azure Databricks documentation is inconsistent on RBAC for Key Vault-backed secret scopes. Some pages instruct granting Key Vault Secrets User to the Databricks service principal directly; others state RBAC is not supported and that Databricks always uses an access-policy entry regardless of vault permission model. If a fresh secret scope ever returns PERMISSION_DENIED despite the RBAC role being correctly assigned, check whether an access-policy entry also needs to be added.

Why Not Just Use a Volume ACL for the Keytab?

A Volume ACL is coarse-grained: read access on the volume gives indefinite access to all files. Key Vault gives per-secret RBAC, versioning, automatic expiry, and an audit log entry for every single read. The keytab belongs in Key Vault.

Base64 Encoding Note

Base64 encoding is NOT encryption. It only makes binary keytab bytes safe to store as a Key Vault text secret. The security comes from the RBAC role assignment and Key Vault's audit log, not from the encoding itself.

1.7Why DBFS is not used

DBFS is not used anywhere in this implementation. There are three distinct reasons.

Cluster-Scoped Init Scripts on DBFS Are End-of-Life

Databricks removed support for storing cluster-scoped init scripts on DBFS root. Setting init_scripts: [{dbfs: {destination: 'dbfs:/path/to/script.sh'}}] in cluster config no longer works. The init script must be sourced from a Unity Catalog Volume.

/dbfs/ Mount Points Are Not Supported on Executors for Init Script Purposes

On SINGLE_USER compute, the FUSE mount that makes /dbfs/... paths appear as a local filesystem is not available during cluster startup (before Spark initialises). An init script that tries to cp /dbfs/path/to/krb5.conf /tmp/kerberos/ will fail at that point.

Keytab Must Never Be on DBFS

DBFS root is a shared, unencrypted storage layer accessible to all users in the workspace. Storing a Kerberos keytab there is equivalent to leaving an AD service account password in a shared folder. The keytab must live in Azure Key Vault, accessed only through the secret scope.

Step 4Create the init script (setup_kerberos.sh)

Owner: Cloud/DevOps admin. Runs on every node at startup (driver, executors and autoscaled nodes) before Spark initialises.

#!/bin/bash
set -euo pipefail

KERB_DIR="/tmp/kerberos"
VOLUME_PATH="/Volumes/<UC_CATALOG>/<UC_SCHEMA>/<UC_VOLUME_NAME>"  # Replace with your UC Volume path
SPARK_ENV="/databricks/spark/conf/spark-env.sh"  # Databricks writes env vars here at startup

mkdir -p "${KERB_DIR}"

# Decode keytab from base64 env var
# KERB_KEYTAB_B64 is set as cluster env var: {{secrets/<scope>/<key>}}
# Databricks resolves it to the base64 keytab string before cluster start.
if [ -z "${KERB_KEYTAB_B64:-}" ]; then
    echo "ERROR: KERB_KEYTAB_B64 is not set. Check the cluster environment variable configuration." >&2
    exit 1
fi
echo "${KERB_KEYTAB_B64}" | base64 -d > "${KERB_DIR}/app.keytab"
chmod 600 "${KERB_DIR}/app.keytab"   # owner read+write only -- keytab is credential-equivalent
chmod 700 "${KERB_DIR}"              # directory: owner traverse only

# Copy config files from UC Volume to local disk
# JVM security framework cannot use /Volumes/ FUSE paths -- files must be local /tmp
cp "${VOLUME_PATH}/krb5.conf" "${KERB_DIR}/krb5.conf"
cp "${VOLUME_PATH}/jaas.conf" "${KERB_DIR}/jaas.conf"
chmod 644 "${KERB_DIR}/krb5.conf"    # world-readable -- JVM reads at auth time
chmod 644 "${KERB_DIR}/jaas.conf"    # world-readable -- JDBC driver reads at connection time

# Security hardening: scrub keytab base64 from spark-env.sh
# After decoding to binary, the base64 string in spark-env.sh is no longer needed.
if [ -f "${SPARK_ENV}" ]; then
    sed -i '/KERB_KEYTAB_B64/d' "${SPARK_ENV}"
fi

echo "Kerberos init complete:"
ls -la "${KERB_DIR}/"
  • Edit one value: set VOLUME_PATH to your own Volume path (see Inputs). The rest is exactly the tested script.
  • Why an init script, not a notebook cell: files written in a notebook exist only on the driver. Init scripts run independently on every node, including nodes added by autoscaling (verified on new nodes).
  • set -euo pipefail: -e exit on any failure, -u fail on unset variables (catches a missing KERB_KEYTAB_B64 early), -o pipefail fail if any step in a pipe fails.
  • Why copy to /tmp: the JVM security framework cannot use /Volumes/ FUSE paths; files must be on local disk.
  • sed on spark-env.sh: Databricks writes resolved secrets to that file. After decoding, the base64 string is removed so no process can read keytab material from it later.

Step 6Store the keytab in Key Vault

Only after the verification in Step 5 succeeds.

6.1 Convert to Base64

Once the test is proven successful, encode the binary keytab to base64. Key Vault stores secrets as text; base64 makes the binary file safe to store that way. Use -b 0 (macOS) or -w0 (Linux) to suppress line breaks — Key Vault must receive a single unbroken string:

# macOS
base64 -b 0 -i /path/to/app.keytab -o /path/to/app.keytab.b64

# Linux
base64 -w0 /path/to/app.keytab > /path/to/app.keytab.b64

Base64 encoding is not encryption. The protection comes from Key Vault’s RBAC and audit log, not from the encoding itself.

6.2 Upload to Azure Key Vault

az keyvault secret set \
  --vault-name <KEYVAULT_NAME> \
  --name <SECRET_KEY> \
  --file /path/to/app.keytab.b64

# Verify the upload succeeded

  --vault-name <KEYVAULT_NAME> \
  --name <SECRET_KEY> \

6.3 Securely Delete Local Copies

Once in Key Vault, local copies are unnecessary and are a security risk:

# Linux — overwrite before deleting
shred -u /path/to/app.keytab /path/to/app.keytab.b64

# macOS — secure delete
rm -P /path/to/app.keytab /path/to/app.keytab.b64
Keep the base64 on a single line (-w0 on Linux, -b 0 on macOS). Key Vault stores the whole string as the secret value, and line breaks would corrupt it.

4.3Why the built-in Spark JDBC reader fails on executors

What Was Tried

df = spark.read.format("jdbc") \
    .option("url", jdbc_url) \
    .option("dbtable", "dbo.PUNCHEVENT") \
    .option("driver", "com.microsoft.sqlserver.jdbc.SQLServerDriver") \
    .load()

The Error

GSSException: No valid credentials provided
  (Mechanism level: No valid credentials provided
  (Mechanism level: Failed to find any Kerberos credenti...))

This error appears on executor nodes only. The same JDBC URL works perfectly on the driver.

Root Cause — Confirmed via Scala Test

The Microsoft SQL Server JDBC driver's Kerberos authentication code path (KerbAuthentication.intAuthHandShake()) calls:

// Inside mssql-jdbc KerbAuthentication
Subject kerberosSubject = /* loaded from JAAS */;
Subject.doAs(kerberosSubject, new PrivilegedExceptionAction<Void>() {
    public Void run() throws Exception {
        // This nested doPrivileged call is the problem
        return AccessController.doPrivileged(new PrivilegedExceptionAction<Void>() {
            public Void run() throws Exception {
                // GSSManager.createCredential() called here
                // At this point, Subject.getSubject(AccessController.getContext()) returns NULL
                // because the UCS DomainCombiner has stripped the Subject from the context
                gssCredential = gssManager.createCredential(...);
                return null;
            }
        });
    }
});

The call chain: Subject.doAs(subject, outer_action) → inside outer_action, AccessController.doPrivileged(inner_action) → inside inner_action, Subject.getSubject(AccessController.getContext()) returns null.

Why on executors only: Databricks UCS (Unified Client Security) installs a custom AccessControlContext with a DomainCombiner on executor JVMs. This DomainCombiner strips the Kerberos Subject from the security context when privilege is escalated via doPrivileged(). On the driver JVM, the Subject's DomainCombiner is not replaced, so the Subject survives the nested call.

Why This Cannot Be Fixed in Configuration

This is not a Kerberos configuration issue. The krb5.conf, jaas.conf, keytab, and SPN are all correct on executors (confirmed by file presence checks and KDC connectivity checks). The failure is in how the mssql-jdbc driver uses Java security APIs inside the Databricks execution environment. It requires changes to either mssql-jdbc (to not use nested doPrivileged) or to UCS (to preserve the Subject through the nested call). Neither change is available.

The unified explanation

On executors, Databricks UCS replaces the security context: the current user becomes root, the global UGI loses its tickets, and the Kerberos Subject is dropped inside nested doPrivileged calls. Spark's MSSQLConnectionProvider.getConnection() (line 67) and the mssql-jdbc Kerberos handshake both depend on that state. A fresh UGI per task, with its own Subject, avoids it, which is Pattern B.

Tested code

5.1What it is and when to use it

Pattern A reads on the driver. The driver opens one Kerberos JDBC connection, collects the rows into memory, and calls spark.createDataFrame() so Spark can distribute them. Executors never touch SQL Server.

Use it forAvoid it for
Connectivity checks, samples and small tablesLarge tables or scheduled bulk loads (use Pattern B)
The first proof that Kerberos works end to endAnything that must scale with the number of executors

Speed is limited to one node (see 5.2).

5.2How it works

Driver loginFresh TGT and service ticket from the keytab
JDBC queryTOP N query over one connection
CollectRows read into Python memory
DistributecreateDataFrame() spreads them to executors
  1. The driver loads the SQL Server JDBC driver and opens one connection. The Kerberos exchange (1.2) happens at this moment: JAAS reads the keytab, the JVM gets a TGT from the KDC, then a service ticket for the SQL Server SPN.
  2. The driver sends a bounded query. SQL Server runs it and streams the rows back over that single connection.
  3. The driver reads the rows one at a time, through the Py4J bridge, into a Python list.
  4. Only then does spark.createDataFrame(rows, cols) hand the list to Spark, which distributes it to the executors.

Only the driver authenticates, so the executor identity problem (4.3) never arises.

How fast is it

  • Speed is set by the driver. There is one connection on one node, so a bigger cluster or more executors do not make it faster.
  • Rows pass through that single connection one at a time and must fit in driver memory.
  • It is the right choice for checks, samples and small tables. For large tables use Pattern B.
  • Test scenario (for reference only): the driver-only baseline read about 250 rows/sec on the test cluster. Your rate depends on VM type, network and SQL Server load.

6.2How it works

PlanDriver warms up executors, reads metadata, computes row-balanced ID ranges
ReadOne task per range: fresh UGI login, then JDBC read of its range
WriteDataFrame appended to a new Delta table
VerifyCounts, then data validated against SQL Server
  1. The driver warms up the executors, reads the table metadata (schema, row count, smallest and largest ID) and splits the ID range into row-balanced partitions sized from executor memory.
  2. Spark starts one task per partition. Each task logs in to Kerberos with its own fresh UGI, opens its own JDBC connection and reads only its ID range, with NOLOCK, a forward-only cursor and a fetch size of 10,000 rows.
  3. Rows stream from SQL Server straight into the executor, one row at a time, and never pass through the driver.
  4. The rows are written to Delta in parallel. The driver compares the Delta count with the source count, and Cell 8 validates the data against SQL Server.

How fast is it

  • Speed grows with the number of tasks running at once (executors multiplied by cores per executor): more slots, faster load.
  • Every task is an independent connection reading its own ID range, and the rows go straight from SQL Server into the executors, never through the driver.
  • Three settings keep each task fast: socketTimeout=0 (long reads do not time out), FETCH_SIZE of 10,000 (far fewer network round trips) and native types (no string conversion).
  • Test scenario (for reference only): a 104M-row, 31-column table loaded in about 4 minutes (about 441K rows/sec) on Standard_D4ds_v5 workers with 4 cores each, autoscaling to 8 executors (32 task slots). The Cell 1 header quotes an earlier run of 4.8 minutes.
  • Actual speed depends on your VM type, cluster size, network and SQL Server load, so measure it on your own cluster. A very large number of tasks can load SQL Server.

6.3Why a fresh UGI works

On executors, Databricks UCS replaces the security context: the current user becomes root, the global UGI loses its tickets, and the Kerberos Subject is dropped inside nested doPrivileged calls. Spark's MSSQLConnectionProvider.getConnection() (line 67) and the mssql-jdbc Kerberos handshake both depend on that state, which is why the built-in reader fails. loginUserFromKeytabAndReturnUGI() builds a new, independent Subject per call, so ugi.doAs(...) works from its own tickets.

  • Aggregates, source versus Delta: MIN, MAX and SUM of the ID and of a numeric measure column, distinct count of a key column, non-null counts per column. CHECKSUM_AGG on the source is a useful reference.
  • Structure: column counts from INFORMATION_SCHEMA.COLUMNS versus Delta, plus the first and last 5 rows by ID.
  • Pass only when row count, ID range, column count and null integrity all match.

Adapt the aggregate and sample columns to your table. A Delta table far smaller than the source (for example 10 to 40x) is normal: Parquet is columnar with dictionary encoding and snappy.

                        val v = rs.getLong(i+1); values(i) = if (rs.wasNull()) null else v
                      case java.sql.Types.BIT =>
                        val v = rs.getInt(i+1); values(i) = if (rs.wasNull()) null else v
                      case java.sql.Types.DECIMAL | java.sql.Types.NUMERIC =>
                        values(i) = rs.getBigDecimal(i+1)
                      case java.sql.Types.FLOAT | java.sql.Types.REAL =>
                        val v = rs.getFloat(i+1); values(i) = if (rs.wasNull()) null else v
                      case java.sql.Types.DOUBLE =>
                        val v = rs.getDouble(i+1); values(i) = if (rs.wasNull()) null else v
                      case _ => values(i) = rs.getString(i+1)
                    }
                  } else {
                    val obj = rs.getObject(i+1)
                    values(i) = if (obj == null) null else obj.toString
                  }
                } catch { case _: Exception => values(i) = rs.getString(i+1) }
                i += 1
              }
              _hasNext = rs.next()
              if (!_hasNext) {
                try { rs.close() } catch { case _: Exception => }
                try { stmt.close() } catch { case _: Exception => }
                try { conn.close() } catch { case _: Exception => }
              }
              Row.fromSeq(values.toSeq)
            }
          }
        }
      })

6.8Autoscaling and cluster sizing

Pattern B plans from the executors it actually finds, so it works on any cluster size. What differs is the cluster type.

The two cluster types

Interactive Cluster (Dev) Job Cluster (ADF/Production)
Example A dev cluster (min=0) Created fresh per ADF run
At rest 0 workers (driver only) Does not exist
When job starts Workers NOT ready (need 30-90s) Workers READY from creation
Warmup needed? YES (critical, 30-90s) Finishes in <5s (just confirms)
After job Stays alive, scales down DESTROYED automatically
Cost Pays for idle time Zero cost when not running
Use for Development, testing Production ADF pipelines

Job cluster lifecycle (ADF production)

  1. Create (before your code runs): Azure provisions the driver and min_workers, the runtime installs, the init script runs on every node and the executors register. All min_workers are ready before your code starts.
  2. Run: the ingestion warms up, plans partitions from the executors it finds and runs one task per partition. If tasks queue, the autoscaler adds workers up to max_workers.
  3. Clean up: the cluster terminates by itself and ADF receives success or failure.

Can we skip the warmup?

Short answer: Keep it. It costs <5s on job clusters.

Scenario Skip warmup? What happens
Job cluster (min=4+) Could, but DON'T Warmup takes <5s. Gives executor count for dynamic sizing.
Interactive cluster (min=0) NEVER 0 executors -> runs on driver -> out of memory or very slow
Job cluster (min=0) NEVER Same problem as interactive

What warmup gives you (even on job clusters): - Confirmed executor count for partition calculation - Confirmed executor memory for safe rows/partition sizing - Confirmed init scripts completed (keytab deployed) - Handles edge cases (slow VM start, spot eviction)

Without warmup, you'd need to HARDCODE partition count (for example, a fixed number regardless of cluster size). That's fragile.

Autoscaling: exactly what happens

Key insight: It does BOTH! 1. min_workers are ready BEFORE code starts (Phase 1) 2. Additional workers (up to max) scale in DURING the job 3. Our code handles both naturally

6.10Using Pattern B inside a JAR (spark_jar_task)

Problem statement

All ADF pipelines using spark_jar_task with <your.package>.DBIngestionDriver that read from SQL Server via Kerberos JDBC FAIL on executor nodes with:

GSSException: No valid credentials provided (Mechanism level: Failed to find any Kerberos tgt)

This affects ALL tables, not just ACCRUALTRAN. Any spark.read.format("jdbc") call with integratedSecurity=true;authenticationScheme=JavaKerberos fails when Spark distributes reads to executors.

Root cause (confirmed)

Component Issue
Spark's MSSQLConnectionProvider Uses UserGroupInformation.getCurrentUser().doAs() (GLOBAL UGI)
Databricks UCS (Unity Catalog Security) Overrides executor JVM's currentUser to root via DomainCombiner
Result Global UGI on executors has NO Kerberos tickets → GSSException

Technical detail: UserGroupInformation.loginUserFromKeytab() stores credentials in the global static UGI. On Databricks executors, the UCS DomainCombiner replaces the Subject, so the global UGI's Kerberos tickets are stripped.

Proven fix (tested & validated)

Code Change Required in JAR

BEFORE (current JAR — FAILS):

// This stores in GLOBAL UGI — UCS strips it on executors
UserGroupInformation.loginUserFromKeytab(principal, keytabPath);
Connection conn = DriverManager.getConnection(jdbcUrl);

AFTER (fix — WORKS):

// Creates a FRESH UGI per task — independent of global state
UserGroupInformation ugi = UserGroupInformation.loginUserFromKeytabAndReturnUGI(principal, keytabPath);
Connection conn = ugi.doAs(new PrivilegedExceptionAction<Connection>() {
    @Override
    public Connection run() throws Exception {
        return DriverManager.getConnection(jdbcUrl);
    }
});

Key Difference

Method Scope Databricks Compatible?
loginUserFromKeytab() Global static UGI NO — UCS strips credentials
loginUserFromKeytabAndReturnUGI() Fresh instance per call YES — bypasses UCS entirely

Mandatory JDBC configuration

jdbc:sqlserver://<host>:1433;
  databaseName=<db>;
  encrypt=true;
  trustServerCertificate=true;
  integratedSecurity=true;
  authenticationScheme=JavaKerberos;
  serverSpn=MSSQLSvc/<host>:1433@<REALM>;
  loginTimeout=60;
  socketTimeout=0           <-- CRITICAL: must be 0 (infinite)

WARNING: socketTimeout MUST be 0. The Databricks shaded mssql-jdbc driver (shaded.databricks.preview_version.com.microsoft.sqlserver.jdbc) overrides/caps non-zero socketTimeout values, causing Read timed out errors even for short queries.

Production requirements

The JAR should implement these for production-grade ingestion:

Incremental / Watermark-Based Reads

// On each run:
// 1. Read last watermark from Delta table metadata or checkpoint
long lastMaxId = spark.table(targetTable).selectExpr("MAX(id)").first().getLong(0);
// 2. Read only NEW rows: WHERE id > lastMaxId
String query = "SELECT * FROM table WHERE id > " + lastMaxId;
// 3. Append to Delta (no duplicates)
df.write.format("delta").mode("append").saveAsTable(target);

MERGE/Upsert for Tables with Updates

MERGE INTO target USING source
  ON target.id = source.id
  WHEN MATCHED AND source.UPDATEDTM > target.UPDATEDTM THEN UPDATE SET *
  WHEN NOT MATCHED THEN INSERT *

Dynamic Partitioning (avoid OOM)

// Compute safe partition size from available executor memory:
long memPerTask = executorMemory / coresPerExecutor;
long safeRows = (long)(memPerTask * 0.40 / estimatedRowBytes);
int partitions = (int) Math.ceil(totalRows / (double) Math.min(safeRows, 1_000_000));

Retry Logic Per Partition

for (int attempt = 1; attempt <= MAX_RETRIES; attempt++) {
    try {
        UserGroupInformation ugi = UserGroupInformation.loginUserFromKeytabAndReturnUGI(principal, keytab);
        result = ugi.doAs(() -> readPartition(startId, endId));
        break;
    } catch (Exception e) {
        Thread.sleep(5000 * (1 << (attempt - 1)));  // Exponential backoff
    }
}

fetchSize Tuning

Statement stmt = conn.createStatement(ResultSet.TYPE_FORWARD_ONLY, ResultSet.CONCUR_READ_ONLY);
stmt.setFetchSize(10000);  // Default is 128 — causes 78x more network round-trips

8.3FAQ (expand any entry)

Can I use a password instead of a keytab?

No. The cluster is non-interactive — there is no way to enter a password at cluster start. The keytab is the only supported mechanism for non-interactive Kerberos authentication.

Can I store the keytab in the UC Volume instead of Key Vault?

No. The keytab is credential-equivalent. A UC Volume ACL is too coarse-grained and does not provide per-read audit logging. Key Vault is the correct storage location.

What happens to the keytab when the cluster shuts down?

/tmp/kerberos/ is part of the node's ephemeral local disk. It is destroyed when the node is terminated. The keytab stays in Key Vault and is re-decoded on every cluster start via the init script.

Why do I need both integratedSecurity=true AND authenticationScheme=JavaKerberos?

integratedSecurity=true enables Windows/Kerberos integrated auth instead of SQL login. authenticationScheme=JavaKerberos further narrows the choice to Java Kerberos specifically (instead of NTLM or NegotiateSSPI). Without the second parameter, the driver may attempt NTLM, which typically fails in cross-platform Linux-to-Windows scenarios.

Can this work on a Standard (shared) cluster?

No. Standard mode does not support spark.executor.extraJavaOptions, and init scripts require an admin-managed allowlist. Both are required for this pattern.

What if the service account password changes?

The keytab must be regenerated and re-uploaded to Key Vault. The cluster must then be restarted. The old keytab will fail with Decrypt integrity check failed if the AD password (and thus KVNO) has changed.

Can I use this on Serverless compute?

No. Serverless compute does not support init scripts or spark.executor.extraJavaOptions. SINGLE_USER classic clusters are required.

Why not use spark.read.jdbc() with keytab/principal options?

Tested and confirmed FAILED. Spark's internal MSSQLConnectionProvider uses the global UGI which Databricks UCS corrupts on executors. See Issue #1.

Why is the Delta table only 741 MB for 104M rows?

Parquet columnar storage + dictionary encoding + snappy compression = 38.7x compression. SQL Server stores 28 GB for the same data. Validated with full checksums.

Why 1M rows per partition and not more/less?

Dynamically computed. With D4ds_v5 (7.6 GB/executor, 4 cores): safe limit = 1.86M rows. Capped at 1M for extra safety margin. Lazy iterator means O(1) memory per row during read.

What if a partition fails?

Retry 3x with exponential backoff (5s, 10s, 20s). If all retries fail, that partition returns empty (doesn't crash job). Validation Cell 8 will detect missing rows.

Can this handle a table whose ID column has a different name, or no numeric ID?

Yes — change ID_COLUMN in Cell 1 to any numeric column. Must be indexed for performance.

Why socketTimeout=0 and not a large value like 3600?

Databricks shaded mssql-jdbc driver overrides/caps non-zero values. Only 0 (infinite) reliably disables the timeout. Tested: 1800 failed, 0 works.

Why mode("append") and not mode("overwrite")?

Safety reviewer blocks overwrite. Append creates table if not exists. For fresh re-ingestion, use a new table name.

Is there a risk of duplicate data with append?

Only if you run Cell 7 twice against the same target table. Solution: always use a new table name, or validate with Cell 8 before and after.

Does it autoscale first, then run? Or during the run?

A: BOTH. min_workers are ready before code starts. Additional workers scale in during heavy load.

Can I skip the warmup?

A: Keep it. On job clusters it takes <5 seconds. It gives you executor count and memory for dynamic partition sizing. Without it you'd need to hardcode.

What mechanism for production?

A: Databricks Job with Job Cluster, triggered by ADF. Fresh cluster per run. min=4, max=8. Auto-terminates. Zero idle cost.

What does ADF need to do?

A: One API call: POST /api/2.1/jobs/run-now with the job ID. Then poll for completion. That's it.

Initial krb5.conf only had the service account's realm:

Round 1: Network hypothesis
Hypothesis: executor nodes could not reach the KDC.

Test: Scala cell on executor:

import java.security.AccessController
val subject = Subject.getSubject(AccessController.getContext())

Subject.doAs(subjectFromJaas, new PrivilegedExceptionAction[Unit] {
    def run(): Unit = {
        val inner = AccessController.getContext()
        val subjectInner = Subject.getSubject(inner)
        println(s"Subject inside doAs: $subjectInner")  // Still null!
    }
})

Result: Subject is null even inside Subject.doAs, when called from an executor.

Root Cause
Databricks UCS (Unified Client Security) on SINGLE_USER clusters installs a custom DomainCombiner in the AccessControlContext of executor JVMs. This DomainCombiner intercepts the security context during AccessController.doPrivileged() calls and strips the Kerberos Subject.

The mssql-jdbc KerbAuthentication class calls Subject.doAs(subject, outer) → AccessController.doPrivileged(inner). Inside the inner doPrivileged callback, the Subject is retrieved via Subject.getSubject(AccessController.getContext()) — which returns null because the UCS DomainCombiner removed it from the context. The subsequent GSSManager.createCredential() call then fails with No valid credentials.

On the driver JVM, UCS does not replace the DomainCombiner in the same way, so the Subject survives.

Decision
Distributed Spark JDBC with Kerberos is not workable on this environment. Standardise on driver-only JDBC pattern. This is a platform constraint, not a configuration issue.

Superseded for large loads. This conclusion was reached before the fresh-UGI technique was found. See Issue 18 and Pattern B.

What was observed
klist -k -t app.keytab output showed:

KVNO Timestamp           Principal
---- ------------------- ------------------------------------------
   0 07/01/26 10:00:00   SVC-sampleapp@PARENT.EXAMPLE.ORG (aes256-cts-hmac-sha1-96)

KVNO=0 instead of the expected value like 4 or 5.

Concern

Connection was tested anyway — it succeeded despite KVNO=0. Issue 16: UCS DomainCombiner — Executor-Side Kerberos Root Cause (Full Technical Detail)

This is the deepest technical issue encountered. It explains why spark.read.format("jdbc") with Kerberos is fundamentally broken on SINGLE_USER Databricks clusters for the mssql-jdbc driver.

The mssql-jdbc internal call chain for Kerberos

// Simplified from KerbAuthentication.intAuthHandShake()
public void intAuthHandShake(PacketReader p, PacketWriter w) throws SQLServerException {
    Subject subject = Subject.getSubject(AccessController.getContext()); // (A)
    if (subject == null) {
        // Fall back to JAAS-based login
        LoginContext lc = new LoginContext("SQLJDBCDriver", ...);
        lc.login();
        subject = lc.getSubject();
    }

    Subject.doAs(subject, new PrivilegedExceptionAction<Void>() { // (B)
        public Void run() throws GSSException {
            return AccessController.doPrivileged(  // (C) -- THIS IS THE PROBLEM
                new PrivilegedExceptionAction<Void>() {
                    public Void run() throws GSSException {
                        // At this point:
                        // Subject.getSubject(AccessController.getContext()) == null
                        // because (C) created a new security context where UCS
                        // DomainCombiner stripped the Subject
                        gssCredential = GSSManager.getInstance().createCredential(...);
                        // ^^^ Throws: No valid credentials provided
                        return null;
                    }
                }
            );
        }
    });
}

Why the Subject is null at point (C)

Subject.doAs(subject, action) at point (B) creates a new AccessControlContext that includes the Subject's DomainCombiner. When AccessController.doPrivileged(inner) is called at point (C), Java creates ANOTHER new AccessControlContext for the inner action. Normally this context would inherit the Subject from the outer doAs.

However, Databricks UCS installs a custom DomainCombiner on executor JVMs. This DomainCombiner's combine() method does NOT preserve the Subject in the resulting AccessControlContext. The result is that Subject.getSubject(AccessController.getContext()) inside the inner doPrivileged returns null.

Why driver is different

The driver JVM's AccessControlContext is not intercepted by the UCS DomainCombiner in the same way. The Subject survives the nested doPrivileged call on the driver. This is why all driver-side JDBC calls work and all executor-side calls fail.

Scala confirmation test

import javax.security.auth.Subject
import java.security.{AccessController, PrivilegedExceptionAction}

// Run this in a Scala notebook cell on an executor partition
val rdd = spark.sparkContext.parallelize(Seq(1), 1)
rdd.map { _ =>
  val outerSubject = Subject.getSubject(AccessController.getContext())
  println(s"Subject before doAs: $outerSubject")

  // Simulate what mssql-jdbc does
  val fakeSubject = new Subject()
  Subject.doAs(fakeSubject, new PrivilegedExceptionAction[Unit] {
    def run(): Unit = {
      val insideDoAs = Subject.getSubject(AccessController.getContext())
      println(s"Subject inside doAs: $insideDoAs")  // Expected: fakeSubject

      AccessController.doPrivileged(new PrivilegedExceptionAction[Unit] {
        def run(): Unit = {
          val insideDoPriv = Subject.getSubject(AccessController.getContext())
          println(s"Subject inside nested doPrivileged: $insideDoPriv")  // UCS makes this null
        }
      })
    }
  })
}.collect()

Actual output from executor:

Subject before doAs: null
Subject inside doAs: javax.security.auth.Subject@...
Subject inside nested doPrivileged: null   <-- UCS DomainCombiner strips it

Final conclusion
This is a fundamental incompatibility between mssql-jdbc's Kerberos implementation (which uses nested Subject.doAs + AccessController.doPrivileged) and the Databricks UCS security subsystem on executor nodes. There is no workaround short of patching mssql-jdbc or UCS. The driver-only JDBC pattern is the correct solution.

Issue 17: Py4J Credential Inspection Limitations

What was tried
After confirming JAAS login worked on the driver, tried to inspect the active Kerberos credentials from Python to verify TGT existence:

jvm = spark._jvm
ctx = jvm.java.security.AccessController.getContext()
subject = jvm.javax.security.auth.Subject.getSubject(ctx)

# Attempt 1: Get credentials by type
creds = subject.getPrivateCredentials(jvm.javax.security.auth.kerberos.KerberosTicket)

Error

Py4JError: Java Object id does not exist in the JVM

# Attempt 2: Pass the class differently
creds = subject.getPrivateCredentials(jvm.java.lang.Class.forName(
    "javax.security.auth.kerberos.KerberosTicket"
))

Error: Same Py4JError.

# Attempt 3: Use JavaClass directly
KT = jvm.javax.security.auth.kerberos.KerberosTicket
creds = subject.getPrivateCredentials(KT)  # Still fails

Root Cause
Py4J represents Java classes as JavaClass objects in Python, but these are not the same as java.lang.Class<T> instances that Java methods accepting type parameters expect. When Py4J tries to pass a JavaClass as a Class<T> argument, the JVM-side Py4J gateway cannot resolve the correct object ID, hence Java Object id does not exist in the JVM.

Workaround (used in validation cell)
Use the unparameterised getPrivateCredentials() (returns Set<Object>), then iterate and filter by class name:

creds = subject.getPrivateCredentials()  # Set<Object> - no type param
for cred in creds:
    name = cred.getClass().getName()     # String comparison works fine via Py4J
    if "KerberosTicket" in name:
        # Inspect TGT details
        end_time = cred.getEndTime()     # Ticket expiry
        print(f"TGT valid until: {end_time}")

Alternative: Shell-level verification

import subprocess
result = subprocess.run(
    ["klist"],  # Show current Kerberos credential cache (if kinit was run)
    capture_output=True, text=True
)
print(result.stdout or result.stderr)

Note: klist without arguments shows the credential cache (from kinit), not the JAAS-obtained TGT. For the JAAS TGT, the Py4J approach above is the only Python-accessible path.

Issue 26: All Columns Stored as StringType

When: earlier ingestion versions used rs.getObject(i).toString for all values - Impact: Downstream queries need CAST(), Delta statistics don't work (lexicographic), 7% larger files - Fix: Added USE_PROPER_TYPES=True flag.
