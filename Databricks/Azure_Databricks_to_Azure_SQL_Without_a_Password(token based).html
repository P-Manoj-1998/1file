Connecting Databricks to Azure SQL Without a Password

How to set up a secure, token-based connection using an Access Connector Managed Identity

All names, IDs and servers here are dummy values. Replace them with your own (lookup table in Section 5). This guide is only about the connection: identity, permissions, network and testing. It is not a notebook tutorial.

1. Goal

Let Databricks (notebooks, jobs, pipelines) connect to Azure SQL Database with no username, no password and no stored secret.

Instead of a password, Databricks asks Azure for a short-lived token, and Azure SQL validates it. A venue analogy helps:

  • Access Connector = your ID badge (proves who you are)
  • Service Credential = the badge holder inside Databricks (people borrow the badge without seeing it)
  • SQL user = your name on the guest list at the door
  • Token = the wristband you get after the badge check (it expires)

Miss any one of those and you don't get in. That's why setup has several steps.

2. Why This Approach

Password-based Managed Identity + Service Credential
Secret to store, rotate and protect Nothing to store
Can leak or be shared Nothing to leak
Tied to a person or shared account Tied to one Azure-managed identity
Hard to audit Access traces back to one identity

Bonus: one Access Connector, many services

The Access Connector identity is not SQL-specific. The same connector can also connect Databricks to Key Vault, Storage accounts and other Azure services: build the identity once, reuse it, and avoid new secrets for every service. Each target service still needs its own permission granted to the connector identity (for SQL, that's the SQL user in Step 3), and every permission is shared by everything using the connector. So grant least privilege, and use separate connectors per environment.

3. Concepts

Concept In plain words Why it's here
Access Connector for Azure Databricks An Azure resource that owns a system-assigned managed identity Databricks has no workspace-level identity. The connector is the identity.
Managed Identity (MI) An Entra ID identity Azure creates and manages, with no password Lets Azure vouch for Databricks
Unity Catalog Service Credential A Databricks object pointing at the Access Connector Hands out tokens by name and hides identity details. Governed by UC permissions.
Credential Type = Managed Identity How the credential authenticates Means "authenticate through the Access Connector"
Purpose = SERVICE What the credential is for See the note below
Entra access token Signed, short-lived (about 1 hour) proof of identity Replaces the password
Contained SQL user (external provider) A database user created FROM EXTERNAL PROVIDER Tells SQL "this Entra identity may log in here"

Purpose matters: SERVICE vs STORAGE. A Unity Catalog credential has a purpose. STORAGE credentials reach cloud storage (external locations). SERVICE credentials reach other cloud services such as Azure SQL or Key Vault using a token. For SQL we need SERVICE. If you pick the wrong one, create a new credential with the right purpose.

4. How the Connection Works

 Databricks          Unity Catalog          Microsoft Entra ID       Azure SQL Database
 (code runs)               │                        │                       │
    │ 1. "token please"    │                        │                       │
    │   (credential name)  │                        │                       │
    │─────────────────────>│                        │                       │
    │                      │ 2. credential ->       │                       │
    │                      │    Access Connector    │                       │
    │                      │───────────────────────>│                       │
    │                      │ 3. issue token         │                       │
    │                      │<───────────────────────│                       │
    │ 4. token returned    │                        │                       │
    │<─────────────────────│                        │                       │
    │                                                                       │
    │ 5. connect over JDBC, pass token as "accessToken"                     │
    │──────────────────────────────────────────────────────────────────────>│
    │                                     6. validate token                 │
    │                                     7. match SQL user [ac-demo-...]   │
    │                                     8. apply db_datareader (SELECT)   │
    │ 9. data returned                                                      │
    │<──────────────────────────────────────────────────────────────────────│

Take-away: the caller only knows a credential name. Identity, token and permissions are handled for it.

6. Before You Start

  • Databricks workspace enabled for Unity Catalog
  • Compute on DBR 15.4 or higher, UC-enabled (service-credential API arrives in 15.4)
  • An Azure SQL Database you can administer
  • People available (see Section 12): an Azure admin, a SQL Entra admin, a Unity Catalog admin. To create the credential in Step 4 you need to be a metastore admin or hold the CREATE SERVICE CREDENTIAL privilege.

Azure role assignment for SQL? Not needed. Azure SQL grants access through database users (Step 3), not RBAC. (Other services, such as Storage and Key Vault, do need roles. See the bonus note in Section 2.)

8. Step-by-Step Setup

STEP 1 · Create the Access Connector

Why: Databricks needs an Azure identity to prove itself to SQL. The Access Connector provides one as a system-assigned managed identity. (It is not a workspace identity; Azure Databricks doesn't have one.)

Do (Azure Portal):

  1. Search Access Connector for Azure Databricks → Create.
  2. Subscription: yours. Resource group: rg-demo-data.
  3. Name: ac-demo-databricks. Region: same as your workspace.
  4. Managed Identity tab: keep System assigned = On.
  5. Review + create.

Note down:

  • Resource ID (Access Connector → Properties): /subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-demo-data/providers/Microsoft.Databricks/accessConnectors/ac-demo-databricks
  • Object (principal) ID (Access Connector → Identity), useful for troubleshooting.

Verify: Identity → System assigned shows Status: On.

STEP 2 · Set a Microsoft Entra admin on the SQL server

Why: SQL can only create users FROM EXTERNAL PROVIDER once the server is linked to Entra ID. Assigning an Entra admin creates that link. Skip it and Step 3 fails.

Do: Portal → SQL server contoso-sql-demo → Microsoft Entra ID → Set admin → demo-sql-admins → Save.

Use a group, not one person, so access doesn't hinge on a single account.

Verify: the admin name shows on that page.

STEP 3 · Create the SQL user and grant read access

Why: Entra proves who is calling. SQL still decides what they may do. This step puts the identity on the guest list with read-only rights.

Do:

  1. Connect to contoso-sql-demo.database.windows.net using Microsoft Entra authentication, as the Entra admin or a member of the admin group.
  2. Select the target database demo_db, not master.
  3. Run:
-- 1. Create a database user for the Access Connector identity
CREATE USER [ac-demo-databricks] FROM EXTERNAL PROVIDER;

-- 2. Read-only access (SELECT on all tables and views)
ALTER ROLE db_datareader ADD MEMBER [ac-demo-databricks];
Rule Reason
Name in [ ] must exactly match the Access Connector name SQL finds the identity by Entra display name, not Object ID or App ID
Run in the target database Users live inside a database. A user in master doesn't open demo_db.
Entra admin must exist (Step 2) Otherwise SQL can't resolve the identity

Verify:

SELECT name, type_desc, authentication_type_desc
FROM sys.database_principals
WHERE name = 'ac-demo-databricks';
-- Expected: EXTERNAL_USER, EXTERNAL

Tighter access? Instead of db_datareader, grant only what's needed: GRANT SELECT ON SCHEMA::Sales TO [ac-demo-databricks];

STEP 4 · Create the Service Credential in Unity Catalog

Why: this wraps the Access Connector in a Unity Catalog object, so Databricks code asks for a token by name and never handles identity details.

Do: Databricks → Catalog → External Data → Credentials → Create credential

Field Value Note
Credential type Service credential Sets the purpose to SERVICE. Don't pick the storage option.
Credential name sqlcred_demo Used later when requesting a token
Access Connector ID /subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-demo-data/providers/Microsoft.Databricks/accessConnectors/ac-demo-databricks Resource ID from Step 1

Verify: open the credential's Overview tab:

Field Expected Meaning
Credential Type Managed Identity Authenticates through the Access Connector
Purpose SERVICE Usable for service-token requests
Limit to read-only use Disabled Leave as is. Read-only is enforced in SQL by db_datareader.

If Purpose shows STORAGE, recreate the credential.

STEP 5 · Set Permissions and Workspaces

Why: anyone who can use the credential can act as the connector identity. These two tabs control who and where.

5A · Permissions tab (who):

GRANT ACCESS ON SERVICE CREDENTIAL `sqlcred_demo` TO `demo-data-engineers`;

Or Credential → Permissions → Grant. Give ACCESS to every user, group or service principal that will connect, including whoever scheduled jobs run as (Section 9). The credential owner already has access.

5B · Workspaces tab (where): confirm the workspace that will connect is allowed to use the credential (open to all workspaces on the metastore, or explicitly listed). Otherwise the credential will look "missing".

Verify: Permissions lists your group, Workspaces includes your workspace, and dbutils.credentials.showServiceCredentials() lists sqlcred_demo.

STEP 6 · Open the network path

Why: perfect authentication still fails if Databricks compute can't reach SQL on TCP 1433.

Option How Best for
A. Private Endpoint (recommended) Create a Private Endpoint for the SQL server in the Databricks VNet (or a peered one). Link private DNS zone privatelink.database.windows.net to that VNet. Production, no-public-access policies
B. Public endpoint + firewall On the SQL firewall, enable Allow Azure services, or add your Databricks compute's public egress IP(s) Dev and quick tests

Verify: the network check in Step 7 passes.

STEP 7 · Test the connection

Why: this proves identity, credential, permission, network and SQL all work together. It's a check, not a deliverable. Run it from any Databricks notebook or job; once it passes, your own code connects the same way.

What every connection needs (this is the whole recipe):

Ingredient Value Why
Token scope https://database.windows.net/.default Tells Entra the token is for Azure SQL
JDBC URL jdbc:sqlserver://<server>:1433;databaseName=<db>;encrypt=true;trustServerCertificate=false;hostNameInCertificate=*.database.windows.net;loginTimeout=30 Encrypted connection with certificate validation. Use databaseName, not database.
Token property accessToken (via the properties argument) Replaces the password

Test (run in order; each check tests one layer):

import socket

# --- Values to replace ---
SQL_SERVER = "contoso-sql-demo.database.windows.net"
DATABASE   = "demo_db"
CREDENTIAL = "sqlcred_demo"
TABLE      = "Sales.Orders"
JDBC_URL = (f"jdbc:sqlserver://{SQL_SERVER}:1433;databaseName={DATABASE};"
            "encrypt=true;trustServerCertificate=false;"
            "hostNameInCertificate=*.database.windows.net;loginTimeout=30")

# Check 1: can the credential be seen?  (fails -> Step 5)
dbutils.credentials.showServiceCredentials()

# Check 2: network  (fails -> Step 6)
socket.create_connection((SQL_SERVER, 1433), timeout=10).close()
print("Network OK")

# Check 3: token  (fails -> Steps 1, 4, 5)
cred  = dbutils.credentials.getServiceCredentialsProvider(CREDENTIAL)
token = cred.get_token("https://database.windows.net/.default")
print(f"Token OK ({len(token.token)} chars)")   # never print the token itself

# Check 4: SQL login and read  (fails -> Steps 2, 3)
df = spark.read.jdbc(
    url=JDBC_URL,
    table=TABLE,
    properties={
        "accessToken": token.token,
        "driver": "com.microsoft.sqlserver.jdbc.SQLServerDriver",
        "applicationIntent": "ReadOnly",
    },
)
display(df.limit(10))

Success: rows from Sales.Orders are displayed.

Use spark.read.jdbc(..., properties=...). The .format("jdbc").option("accessToken", ...) style does not forward the token to the SQL Server driver.

9. Who Will Connect? (Users, Jobs, ADF)

The connection setup is identical for everyone. Only the identity running the code differs, and that identity needs ACCESS on the credential (Step 5).

Who runs it Identity used What to do
Interactive user (any cluster mode) The user Add them to a group that has ACCESS
Scheduled job Job owner or run_as identity Grant ACCESS to that identity. Cluster: DBR 15.4+, Single User (recommended) or Shared.
ADF-triggered job (recommended) The service principal ADF uses to call the Jobs API Add the SP to the workspace and to a group with ACCESS; give it CAN_MANAGE_RUN on the job
ADF "Notebook" activity (legacy) The linked-service identity Same ACCESS grant; cluster must be DBR 15.4+, Single User 
ADF (service principal) ──triggers──> Databricks Job ──runs──> your code
                                                                  │
                                  Service Credential <────────────┘
                                  (Access Connector MI) ──token──> Azure SQL

ADF never talks to SQL. It only starts the job. The credential handles SQL authentication inside the job.

"Works for me, fails on schedule" almost always means interactive runs as you and the job runs as someone else. Grant ACCESS to the run_as identity.

10. Gotchas (and Why)

# Do this Not this Why
1 spark.read.jdbc(..., properties={"accessToken": ...}) .format("jdbc").option("accessToken", ...) .option() doesn't pass accessToken to the driver
2 databaseName=demo_db database=demo_db The Microsoft driver only recognises databaseName
3 CREATE USER [ac-demo-databricks] Object ID / App ID / alias SQL resolves the identity by name
4 Run CREATE USER in the target DB Running it in master Users are per database
5 Set the Entra admin first Skipping Step 2 FROM EXTERNAL PROVIDER needs it
6 Credential purpose SERVICE Purpose STORAGE Code asks for a service credential
7 Fresh token for each connection Reusing an old token Tokens expire after about 1 hour
8 Log token length or claims only Printing the token It's a live credential until it expires

11. What Can Break Later

Event Effect What to do
Access Connector deleted and recreated New connector = new identity, so the old SQL user no longer matches (and the same goes for Key Vault / Storage grants) Drop the old SQL user, redo Step 3, re-grant on other services, and update the credential's Access Connector ID
Credential recreated or renamed Code using the old name fails Update the name; re-grant ACCESS
User leaves a group They lose ACCESS Re-add them, or run via a service principal
Network or firewall change Timeouts at Check 2 Revisit Step 6
Long read outlives the token Failure mid-run Split into smaller reads, each with a fresh token

Troubleshooting

Symptom Likely cause Fix
Credential missing from showServiceCredentials() No ACCESS, workspace not allowed, or wrong purpose Step 5; check Purpose = SERVICE in Step 4
Unable to access service credential Running identity lacks ACCESS Step 5A (for jobs, the run_as identity)
credentials API not found / empty token DBR too old or compute not UC-enabled DBR 15.4+ on UC-enabled compute
Cannot open server / TCP timeout Network blocked Step 6: private endpoint, DNS link, firewall
Login failed for <token-identified principal> Identity isn't a SQL user in this database Step 3, in the target DB
SELECT permission was denied User exists, no read role ALTER ROLE db_datareader ADD MEMBER [...]
Principal '...' could not be found during CREATE USER No Entra admin, or name mismatch Step 2; name must equal the connector name
FAILED_JDBC.CONNECTION Used .format("jdbc").option(...) Use spark.read.jdbc(properties=...)
Invalid object name 'Sales.Orders' Wrong schema or table Query sys.tables
ADF returns 403 SP not in workspace or lacks job rights Add to workspace; grant CAN_MANAGE_RUN

Versions: service-credential API needs DBR 15.4+ (16.2+ recommended) on Unity Catalog-enabled compute. On serverless, spark._jvm isn't available, but the spark.read.jdbc approach in Step 7 still works.
